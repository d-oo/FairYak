`git status`, `git diff`(스테이징 여부 상관없이 전부), 그리고 최근 맥락 파악을 위해
`git log`를 확인한 뒤 커밋 메시지를 작성합니다.

## 하지 말 것

- `git add`, `git commit`, `git stash` 등 실제로 작업 트리/히스토리를 바꾸는 명령은
  **절대 실행하지 않습니다.** 메시지만 만들어서 보여주고, 커밋은 사용자가 직접
  합니다.

## 메시지 작성 규칙

- **핵심만 남깁니다.** "무엇이 왜 바뀌었는지" 한 줄 요약 + 불릿 몇 개 수준으로
  정리하고, 세부 구현 디테일(어떤 함수/컴포넌트를 썼는지, 값이 몇 px인지, 어떤
  라이브러리를 썼는지 같은 것)은 뺍니다.
- 형식은 **한 줄 요약 제목 + 빈 줄 + 하이픈 불릿, 한국어**입니다. 이 저장소의 예전
  커밋은 한 줄 제목만 있지만 그 형식은 따르지 않습니다(사용자 요청 — 이 형식으로 통일).
  불릿이 한두 개로 끝날 만큼 작은 변경이어도 제목 + 불릿 형식을 유지합니다.
- **항상 `git status`/`git diff`로 보이는 작업 트리 전체를 기준으로 정리합니다.**
  지금 대화 세션에서 직접 만든 변경인지, 이전 세션이나 사용자가 직접 손댄 변경인지는
  구분하지 않습니다 — 커밋은 지금 작업 트리에 있는 전부를 대상으로 하므로, "이번
  세션에서 안 건드렸다"는 이유만으로 diff에 실제로 있는 변경을 메시지에서 빼면 안
  됩니다.
- 정말로 무관한 변경(예: 이번 커밋 내용과 논리적으로 이어지지 않는 실험적 흔적, 작업
  중 실수로 섞인 파일처럼 봐도 하나의 이야기로 묶이지 않는 것)이 섞여 있을 때만 메시지
  본문에서 빼고, 그런 게 있다는 사실만 커밋 메시지 밖에 짧게 덧붙입니다. 이 판단은
  "세션에서 건드렸는지"가 아니라 diff 내용 자체를 보고 합니다.
- **`docs/todos.md` 같은 md 문서 수정은 특별한 이유가 없으면 변경사항 불릿으로 쓰지
  않습니다**(사용자 요청). todos 항목 추가/삭제, 문서 설명을 코드에 맞게 고친 것, 주석성
  정리처럼 코드 변경에 딸려 온 문서 수정은 메시지에서 빼고, 커밋 메시지 밖에 따로
  언급하지도 않습니다 — 위의 "diff에 있는 변경을 빼지 않는다" 규칙의 의도된
  예외입니다. 쓰는 경우는 예를 들어 커밋이 문서 수정만으로 이뤄져 그 자체가 커밋의
  내용일 때, 또는 새 환경변수·셋업 절차처럼 다른 사람이 알아야 개발/배포가 되는 변경일
  때처럼, 문서 변경이 그 자체로 알려야 할 이유가 있을 때뿐입니다.
- 결과는 그대로 복사해 쓸 수 있게 코드 블록 하나로 보여줍니다.
